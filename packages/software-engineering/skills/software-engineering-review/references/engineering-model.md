# 软件工程最小生成模型

这是把成熟工程方法变成执行时判断的工作参考，不是 SWEBOK 全书摘要，也不是一套新调度器。
先看问题涉及的段落，不要求每次把全部内容展开。来源编号见 sources.md。

## 1. 从需要得到需求，不从症状直接得到补丁

一个用户需要，先变成可观察的成功条件，再进入设计：
`谁在什么环境下做什么 → 可观察结果 → 不可牺牲的约束`。

例如“子对话不再干扰正常工作”，不等于“减少几个弹窗”。
实际需要可能包括：目标身份不变、既有对话可继续、消息间隔受约束、
不抢占用户窗口、发送结果可确认。具体数值来自当次授权，不写成所有项目的常量。

先检查拟定的要求是否真能满足用途，再检查实现是否符合要求。
需求验证、实现验证和实际使用验收可以相互修正，不是一次走完的瀑布流程。[S1][S3]

**最小记录：** 一个结果、一组不能破坏的条件、一个明确不做的事情。
已有 spec/issue 能表达它们就引用，不另建重复需求表。

## 2. 模块边界：按责任和变化隔离，不按名字或工作顺序切块

组件是承担责任并提供接口的单元；它不必对应一个仓库、文件或进程。
审查一个接口时，问：调用者为了使用它，需要知道多少内部细节？
某项内部实现变化，会迫使多少消费者一起修改？

信息隐藏和降低耦合的实际价值，是把常见变化限制在明确边界内，而不只是把代码分成更多文件。
模块化的效果取决于分解标准；增加层数本身不是收益。[S2]

**所有权**指谁依据什么规则接受某个状态转移，不等于“物理上只能有一份数据”。
副本、缓存、事件日志、派生视图可以合理存在；必须说清写入权、冲突处理、读取一致性和恢复方式。
危险的是多处可以各自修改同一事实，却没有明确一致性合同。

优先修改真正拥有缺陷行为的边界。增加适配器时，只翻译契约差异；
不要顺便复制对方的业务状态、认证系统、恢复机制或工具目录。

### 2.1 组合正确性：局部正确不自动推出系统正确

若组件 A 满足自己的不变量、组件 B 也满足自己的不变量，不能因此直接推出 `A+B` 的系统正确性。
还必须检查它们的交互合同：身份是否一致、状态是否正交、谁能接受同一转移、顺序/失败语义是否兼容、一个组件的合法输出是否可能成为另一个组件的非法输入。

最危险的情况不是某个组件明显错误，而是出现“**合法局部状态 + 非法组合状态**”。例如 registry 合法保存一条 watch，Sidecar 合法报告同一 UUID 不可挂载；两个组件都符合自己的局部规则，但“已注册意味着真实可监督”的系统承诺已经失败。

结构性变更先做一次有界 overlap scan：

`概念/状态 → authoritative owner → writers/acceptors → derived views/caches → consumers`

如果新需求与现有机制部分重叠，先判断四种关系：

1. **复用 owner 接口**：新行为只是已有事实的新消费者；
2. **派生 projection**：需要第二份读模型，但它可重建、不可独立改写事实；
3. **抽 shared primitive**：两个机制其实在表达同一个上游责任，继续并排增加会制造补偿逻辑；
4. **保持独立**：概念真正正交，只需要明确交互合同，不应为了“统一”强行合并。

抽象不是 DRY。两段相似代码不一定共享责任；多个物理副本也不等于多个 authority。反过来，两个不同仓库/进程若都能独立决定同一业务事实，就是实际的 ownership 重叠。

**架构轨迹信号：** 如果连续修复开始出现 `sync/reconcile/mirror/fallback`、跨组件补偿、重复 lifecycle/identity/authorization、多个 writer，先问当前分解是否错误。失败应推动模型/边界更新，而不是只新增下一条例外规则。

组合审查的停止条件也要明确：若只有一个 owner、没有共享转移/协议变化、没有重复边界失败，就回到局部工程流程；不要为简单 bug 画全系统图。

## 3. 依赖：必须带操作、阶段和证据

记录需要用到的边，而不是先绘制全系统图：

`A --[要完成的操作 / 阶段 / 证据]--> B`

阶段可以是构建、安装、启动、某次请求、持续运行、停止或恢复。
同一个 B 可能是启动的必需依赖，却不是已启动进程继续工作的必需依赖。
可选遥测、诊断工具和调用者自己的包装器，也不能自动升级为被调用组件的运行依赖。

证据可以来自现有公开契约、真实调用链、配置选择的分支或有界实验。
字符串检索只找到线索：没搜到名字不能证明独立，文件中出现名字不能证明必需。
将边分成已确认、假设、未知；当前行动不依赖的未知，不应阻止整个项目。

**反事实问题：** 在指定阶段，B 不可用时，A 的哪一项承诺无法履行？
这首先是推理问题，不是授权拔掉生产依赖。

## 4. 合同与状态：用前置、后置和不变量定义正确性

前置条件规定合法调用；后置条件规定该调用承诺的结果；
不变量规定相关操作前后必须维持的关系。[S4]
不变量必须有作用域，不要求系统在每条内部指令之间都暴露完整稳定状态。

接口最少要说明对象身份、输入输出、状态转移和失败含义。涉及外部副作用时，
再补权限、幂等性、顺序、重试和取消语义。

判断服务时，只展开与此次决策有关的维度：
进程存在、服务能接受特定工作、目标已绑定、执行在推进、任务已完成、调用获授权。
这些不是必须新增的六个数据库字段。现有接口能表达就不新建状态系统。

健康检查的含义由检查合同决定。监听端口或健康 HTTP 成功不能证明目标已经接管；
空注册集合也不能说明进程坏了。Kubernetes 将启动、存活和就绪检查区别处理，
可借鉴这个分离思路，不必引入 Kubernetes。[S5]

## 5. 不确定性：通信结果不是远端事实

超时可能发生在副作用之前、期间或之后。调用者没收到回执，不代表远端没执行。
先保留原请求身份，读取对应结果；只有真实接口承诺幂等时，才按同一键和同一意图重试。
“生成一个新的请求 ID”不是去重。取消请求被接受也不代表执行已停。[S6]

一次请求成功、一次 assistant turn 结束、子任务完成和用户目标达成都有不同作用域。
审计只收到标题或半句话，属于证据不完整，不能从缺失内容推导“无风险”。
旧终态不得直接成为同一对象上新任务的终态。

不要给每个系统强塞 epoch、租约或消息队列。先展示旧事件可能越权的具体顺序；
现有 request/turn 标识已经能区分时就复用。

## 6. 配置与发布：代码存在不等于能力已上线

在部署相关问题中分别确认：
`源码修订 → 构建制品 → 安装选定项 → 实际运行实例 → 目标端可见行为`。[S7]

这些检查可以读取现有信息，不意味着另造五张表。关键证据应带主机、
目标、版本或实例以及观察时间。主机 A 的 localhost 不能代表主机 B。

缓存历史证据可以减少工作，但不能扩大它原本的作用域。
在发布、重启、登录、目标切换或明显冲突之后，重新观察受到影响的事实；
不要求每个无关动作都重新跑全套健康检查。

文本已被程序输出、客户端已送进模型上下文、模型已遵循、程序已拒绝错误动作，是四种证据。
一个工具结果里的“不可覆盖”不会自行变成宿主的 system 指令或执行权限。
同样，Skill 被发现和读取，不等于每轮必读或永远服从。

## 7. 取舍与规模：用具体场景选方案

先选择最影响用户目标的质量要求，例如变更容易、恢复可靠、交互不受扰或成本可控。
把它写成“发生什么刺激 → 什么环境 → 系统怎样响应 → 如何判断可接受”。
比较零改动、局部修复和新组件时，说明得到什么、付出什么；
一个质量属性的提升可能损害另一个。[S8]

不要凭“微服务”“Agent”“实时”等名词直接选数据库或消息队列。
也不要用用户数量阈值替代安全、数据一致性和团队运维能力判断。
采用更成熟的现有接口通常更省事，但调用前仍需确认授权和关键前置条件。

重复性机械约束尽量由对象 owner 的代码检查，判断性问题用模型辅助。
不要把文本提醒的作用夸大为硬保证。

## 8. 证据与行动：检查服务于决定，不服务于测试数量

形成一个工作便笺即可：

`结果 | 因果模型与首个关键未知 | 不变量 | 反例 | 最小行动与回退 | 证据与下一判断`

例：
- 结果：在指定对话继续已有任务，不产生新对话。
- 模型：服务可访问；指定 UUID 尚未确认在当前主机可见；辅助启动脚本是否相关未知。
- 不变量：不替换身份，不重放结果未知的发送。
- 反例：看到的是另一台机器的 relay，或目标消失后自动创建替代对话。
- 行动：只读查询目标 owner；找到正确目标后，才使用授权的标准接口。
- 证据：准确身份、状态、观察时间；没有找到时只报告这一范围内的未知。

局部编辑用局部检查。跨边界修改用合同/集成检查；发布承诺需要制品和目标环境回读；
外部可见承诺需要有界真实验证。风险升级时才扩大测试范围。

能用可逆、低成本行动区分解释时，就行动，不无限完善模型。
反馈若推翻假设，修改模型；不要只添加一条新的例外规则。
向用户报告判断、关键观察、什么会推翻判断，以及尚未验证的边界。
